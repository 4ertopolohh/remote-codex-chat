# RC-012: CloudPub primary-source findings

Checked 2026-10-05. Scope: official CloudPub documentation and project repository for a Windows localhost service exposed over HTTPS. This note distinguishes documented behavior from checks that still require a live tunnel.

## Install and publish on Windows

- The [quick start](https://cloudpub.ru/docs/) currently offers a Windows x86_64 GUI client and a CLI ZIP named `clo-3.5.1056-stable-windows-x86_64.zip`. The [changelog](https://cloudpub.ru/docs/changelog) dates 3.5.1056 to 2026-09-01. The ZIP should be extracted; adding its directory to `PATH` is optional. Check the actual installed binary with `clo --version` (`-V` is documented), rather than assuming the download page and local installation match. [Quick start](https://cloudpub.ru/docs/), [CLI reference](https://cloudpub.ru/docs/cli)
- The CLI can authorize interactively with `clo login`; its reference says login saves an API token in a config file. The quick start also documents `clo set token <token>`, but a real token must not be put in a repo command, log, issue, or screenshot. For a local HTTP listener on port `PORT`, the documented command is `clo publish http PORT`; CloudPub reports a public `https://...cloudpub.ru` URL and automatically issues a certificate for that hostname. The URL is assigned per publication, so do not hardcode the example hostname. [Quick start](https://cloudpub.ru/docs/), [HTTP/HTTPS guide](https://cloudpub.ru/docs/http), [CLI reference](https://cloudpub.ru/docs/cli)
- `clo publish http PORT` targets `localhost` if the host is omitted; `clo publish http HOST:PORT` can target another locally reachable host. A local HTTP service gets a public HTTPS endpoint; `clo publish https PORT` is for an HTTPS **origin**. CloudPub can add or override upstream request headers, including `Host`, with `--header`/`-H` if the origin requires it. [CLI reference](https://cloudpub.ru/docs/cli), [HTTP/HTTPS guide](https://cloudpub.ru/docs/http)
- `clo publish` saves and starts a resource/agent; `clo register` saves without starting, and `clo run` starts saved publications. `clo ls`, `clo ping`, `clo service status`, and `clo --version` are documented, useful diagnostics. A Windows service requires an administrator console and uses its own config at `C:\ProgramData\cloudpub\client.toml`, separate from the interactive user's config under `%APPDATA%\cloudpub`; its logs are under the system profile. Therefore an interactive login need not configure a service instance. [CLI reference](https://cloudpub.ru/docs/cli), [FAQ](https://cloudpub.ru/docs/faq), [Windows service guide](https://cloudpub.ru/docs/blog/version-2.4.5)

## WebSocket and tunnel behavior

- CloudPub documents forwarding HTTP connections to the local service and describes an internal WebSocket transport between its agent and server. The latter **does not by itself establish** support for forwarding an application's WebSocket Upgrade through a published HTTPS endpoint. I found no explicit public guarantee in the [HTTP/HTTPS guide](https://cloudpub.ru/docs/http), [FAQ](https://cloudpub.ru/docs/faq), or [technical article](https://cloudpub.ru/docs/blog/2025/08/11/cloudpub-2x-tech) about application-level WSS forwarding, idle timeouts, or preservation of `Origin`/`Host`/`X-Forwarded-*` headers. Treat all of these as empirical integration checks, not assumed product guarantees.
- A focused live check should request the app through the assigned HTTPS hostname, open `wss://<assigned-host>/<app-ws-path>` from a browser, confirm a `101 Switching Protocols` handshake and bidirectional messages, then observe an idle connection and reconnect. Compare request headers reaching the local app before changing any origin or trusted-proxy configuration. This is a proposed verification procedure derived from the documentation gap, not a CloudPub instruction. [HTTP/HTTPS guide](https://cloudpub.ru/docs/http), [CloudPub technical article](https://cloudpub.ru/docs/blog/2025/08/11/cloudpub-2x-tech)

## Optional domain and access controls

- A CloudPub assigned hostname works without a custom domain. For a custom domain, the [domain guide](https://cloudpub.ru/docs/domains) requires adding the domain to a publication in the dashboard, configuring the exact CNAME (subdomain) or A (apex) and TXT verification records shown there, and waiting for DNS verification and automatic certificate issuance. This is account/DNS work, not a prerequisite for a basic tunnel. [Domain guide](https://cloudpub.ru/docs/domains)
- CloudPub offers publication-level Basic and Form authentication and email/role ACLs. Its [auth guide](https://cloudpub.ru/docs/auth) says both Basic and Form can protect HTTP/HTTPS, while the [CLI reference](https://cloudpub.ru/docs/cli) currently lists only `none`/`basic` values for `--auth`; verify `clo publish --help` on the installed version before relying on `form`. CloudPub auth is a separate gateway layer; whether either mode preserves this application's cookie-backed WSS flow requires a live test. [Auth guide](https://cloudpub.ru/docs/auth), [CLI reference](https://cloudpub.ru/docs/cli)

## VPN and network caveat

- CloudPub markets access without a VPN, but I found no official statement guaranteeing compatibility with a VPN active on the Windows host or remote phone, nor routing instructions for split tunneling. The documented VPN-specific caveat is that IP geolocation filters can be inaccurate for VPN/proxy users. For a tunnel connection failure, compare `clo ping` and HTTP/WSS access with the actual network routes in use, and inspect the documented Windows logs; do not attribute the failure to VPN without evidence. [CloudPub home](https://cloudpub.ru/), [Filtering guide](https://cloudpub.ru/docs/filter), [CLI reference](https://cloudpub.ru/docs/cli), [FAQ](https://cloudpub.ru/docs/faq)
