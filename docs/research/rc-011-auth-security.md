# RC-011 authentication and security boundary: primary-source findings

Checked 2026-10-05 against [RC-011](https://github.com/4ertopolohh/remote-codex-chat/issues/12). This note distinguishes source requirements from proposed implementation choices for this single-user app.

## Password and login

- Store an Argon2id hash, never plaintext or a fast digest. OWASP's current minimum is `m=19456 KiB`, `t=2`, `p=1`; benchmark on the deployment host. `argon2-cffi`'s `PasswordHasher` uses Argon2id and a random salt, and supports `verify()` and `check_needs_rehash()`. The setup command should generate a hash offline and configuration should load only that hash. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [argon2-cffi PasswordHasher](https://argon2-cffi.readthedocs.io/en/stable/api.html#argon2.PasswordHasher)
- Use a generic failure response for incorrect credentials and throttle repeated login attempts. For this fixed single-user identity, a per-account attempt budget is necessary even when an attacker changes IP; a separate per-IP budget can limit request volume. A `429` response should not disclose the bucket or detailed counter. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP Bot Management](https://cheatsheetseries.owasp.org/cheatsheets/Bot_Management_and_Anti-Automation_Cheat_Sheet.html)

## Server-side sessions and cookies

- Generate opaque, unpredictable IDs with a CSPRNG (OWASP recommends at least 128 random bits for a custom ID). Store identity and an absolute expiry server-side; enforce expiry on every protected request and invalidate the record on logout. Browser cookie deletion alone cannot revoke a stolen ID. Using `secrets.token_urlsafe(32)` and storing only a digest of the token in the session table are sensible implementation choices, not mandated algorithms. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- Session cookies should be `HttpOnly`, `Secure` over remote HTTPS, explicitly `SameSite=Strict` or `Lax`, host-only (no `Domain`), and scoped by `Path`. Set a compatible cookie lifetime but rely on the server expiry as authority. `__Host-` requires `Secure`, no `Domain`, and `Path=/`; a local HTTP development mode therefore needs a plain cookie name or HTTPS. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- Starlette `SessionMiddleware` creates signed cookie-based sessions and makes their contents readable by the client. It does not alone provide RC-011's opaque, server-side, individually revocable sessions. A small application session store is the appropriate seam. [Starlette Middleware](https://www.starlette.io/middleware/), [RC-011](https://github.com/4ertopolohh/remote-codex-chat/issues/12)
- Do not place session IDs or Codex credentials in `localStorage`/`sessionStorage`; JavaScript in the origin can read them. Set `Cache-Control: no-store` for responses with session identifiers or sensitive session data. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## CSRF, CORS, and WebSocket

- Protect authenticated state-changing HTTP operations with a server-validated CSRF mechanism. For a stateful session, a synchronizer token is a supported pattern; a custom request header plus an explicit CORS allowlist is another API pattern. `SameSite` is defense in depth outside OWASP's narrow documented conditions. Check `Origin`/`Referer` against the intended target where using origin validation, and reject missing or `null` source origin unless another CSRF defense succeeds. Do not trust client-supplied `X-Forwarded-*` as the target origin. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- With credentialed cross-origin HTTP requests, configure exact allowed origins; a wildcard is unsuitable. Prefer a same-origin built frontend/API deployment, which avoids production credentialed CORS entirely. FastAPI's `CORSMiddleware` covers HTTP CORS requests; the WebSocket handshake needs its own checks. [FastAPI CORS](https://fastapi.tiangolo.com/tutorial/cors/), [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)
- Authenticate the session **and** validate the browser `Origin` against an explicit allowlist before accepting `/ws/chat`. Browser WebSockets can automatically send cookies and can be initiated cross-site. Browsers send `Origin`, but non-browser clients can forge it, so origin validation is CSWSH protection rather than authentication. Reject absent/`null` origins unless a separate trusted non-browser client mode is deliberately defined. Recheck session validity during long-lived connections, especially before privileged messages; logout should close/invalidate active connections. [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html), [MDN Writing WebSocket Servers](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers)
- The browser `WebSocket()` constructor accepts a URL and optional subprotocols, not arbitrary HTTP headers. Cookie-backed auth is compatible with the existing browser transport; a CSRF value can be added to the handshake only with an intentional protocol mechanism. Avoid putting session secrets in URL query strings, which may enter logs. [MDN WebSocket constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket), [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)

## Remote transport boundary

- Public browser traffic must use HTTPS/WSS. A TLS terminating proxy can forward to localhost over HTTP; trust forwarded host/protocol information only from explicitly trusted proxy IPs, and configure the proxy to overwrite client-provided forwarding headers. This matters for secure-origin calculations and redirects. Keep the app server bound to loopback for the tunnel path, as RC-011 requests. [FastAPI HTTPS and proxy headers](https://fastapi.tiangolo.com/deployment/https/), [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [RC-011](https://github.com/4ertopolohh/remote-codex-chat/issues/12)

## Focused verification

Test unauthenticated, expired, and logged-out HTTP/WS access; valid and invalid password verification; cookie flags in local and remote modes; CSRF missing/wrong/correct values; exact and wrong WebSocket origins; throttling across source IP changes and across restarts if persistence is promised; and long-lived WebSocket expiry. These cases follow the specific failure modes in [RC-011](https://github.com/4ertopolohh/remote-codex-chat/issues/12), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), and [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html).
