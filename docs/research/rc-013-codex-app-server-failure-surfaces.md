# RC-013: Codex app-server failure surfaces relevant to remote reads

Checked 2026-10-05. Scope: OpenAI's version-tagged `rust-v0.160.0` documentation and first-party issue reports. These sources describe possible app-server failures; they do **not** establish the cause of this project's CloudPub disconnections or missing usage data.

## Versioned protocol and behavior

- `model/list` checks the startup model provider against current managed requirements even when a catalog is cached. A provider that no longer meets them returns JSON-RPC `-32600` asking the client to restart Codex; failure to load requirements also blocks the read. Thus a live app-server process is insufficient evidence that model listing will work. [0.160.0 app-server README](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server/README.md#model-catalog-provider-requirements)
- For a saved ChatGPT login, the app-server discovers selected workspace routing at startup, login, or workspace switch. The versioned README says a failed discovery for a selected workspace makes `account/read` return an error; a later read retries. The `account/updated` notification is followed by fresh `configRequirements/read` and `account/read` reads. These are upstream account semantics, distinct from this application's browser WebSocket. [0.160.0 app-server README](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server/README.md#selected-workspace-routing)
- `account/rateLimits/read` is a separate JSON-RPC request from `model/list` and `account/read`. The protocol's rolling `account/rateLimits/updated` event is sparse: clients merge it with the last read or refetch. A missing update is not proof that the app-server connection is down. [OpenAI protocol request definitions](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server-protocol/src/protocol/common.rs), [rate-limit types](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server-protocol/src/protocol/v2/account.rs). This project's response-shape research is in [RC-010](rc-010-runtime-usage.md).
- OpenAI's integration guidance says `model/list` may expose a bundled catalog and should be treated as a catalog, not a model entitlement check. A successful inference turn checks access for that request. This guidance is for a specific OAuth/provider configuration and cannot by itself diagnose the project's saved CLI login. [OpenAI Developers: Codex app-server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

## Related first-party reports, as analogies only

- [#50923](https://github.com/openai/codex/issues/50923) reports Windows Desktop app-server 0.160.0 concurrent-turn stalls, an `account/read` `-32603` routing timeout near 15 seconds, and separate model/MCP discovery delays. The reporter explicitly leaves the internal stalled stage and root cause unresolved. It is a Desktop case, not this project's CloudPub path.
- [#49827](https://github.com/openai/codex/issues/49827) reports Windows app-server 0.159.2 `turn/start` routing failures while native `codex exec` succeeded. Its control demonstrates that successful CLI inference does not prove app-server turns healthy; it says nothing direct about this app's browser transport or rate-limit read.
- [#51052](https://github.com/openai/codex/issues/51052) reports app-server 0.160.0 `account/read` succeeding on Windows and timing out on WSL2 with the same account; `codex exec` succeeded on both. Its platform contrast is particularly unsuitable as evidence of a Windows-hosted application's cause. The report also states that the 15-second error does not identify the stalled internal stage.

## Diagnostic implication

To separate layers in this project, capture independently: (1) browser-to-app HTTP and WebSocket results through CloudPub, (2) backend-to-app-server request IDs, method names, durations and sanitized JSON-RPC error codes/messages for `model/list`, `account/read`, and `account/rateLimits/read`, and (3) whether the app-server child remains alive. This is an inference from the distinct documented operations and issue controls above, not an OpenAI prescribed procedure. Never record credentials or account identifiers in these diagnostics.

## Follow-up: saved-thread read and writer ownership

### Local incident result (2026-10-05)

With the browser and backend stopped, a fresh `codex app-server` 0.160.0 process resumed the affected saved thread in about 0.2 seconds. `thread/read` without turns returned immediately; the same request with `includeTurns: true` exceeded a 12-second deadline. After that timed-out full-history request, unrelated `model/list` and `account/rateLimits/read` on the same process also timed out. A fresh process answered both immediately. The affected rollout is valid JSONL (about 788 KB, 142 records); no transcript content was needed for this differential test. This locates the reproducible failure at Codex app-server full-history hydration for this saved thread. The internal reason that Codex stops responding during hydration remains unknown.

`thread/turns/list` returned four turns and the first `thread/items/list` page returned ten items immediately, but the next items page timed out. Per-turn item reads also timed out for three turns. Thus pagination is not a verified complete recovery path for this particular thread. The application mitigation reads history in a disposable app-server process with a short deadline, closes that process on failure, and leaves the main app-server available for models, usage, and new chats. The affected saved chat can still report `thread_unavailable`; it is not silently presented as a complete transcript.

Local observation supplied for this investigation: the production app-server accepted `thread/resume` for a saved thread, then `thread/read` exceeded a 60-second client deadline; a simultaneous `account/rateLimits/read` exceeded 10 seconds. A fresh app-server answered `model/list` and usage reads but returned `-32600`, `thread <THREAD> already has an active writer`, when asked to resume that same thread. The rollout was reported as about 788 KB and 142 valid JSON lines. These observations do not locate the wait inside Codex.

- In 0.160.0, `thread/read` first reads pending metadata, checks for a loaded thread, then reads persisted metadata/history. With `includeTurns: true`, a loaded legacy thread additionally calls its live `load_history`; a paginated thread persists and hydrates full turns. With `includeTurns` omitted or false, full turn history is skipped, although metadata and live status still require awaited work. The protocol explicitly defaults `includeTurns` to false and recommends paged `thread/turns/list` and `thread/items/list` for paginated history. Therefore the 788 KB rollout size alone does not establish that the timed-out call parsed that full file; the request parameters and history mode matter. [0.160.0 thread processor](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server/src/request_processors/thread_processor.rs), [thread read parameters](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server-protocol/src/protocol/v2/thread.rs)
- The writer error is produced by an exclusive, cross-process lock for that thread under the Codex home. A failed nonblocking lock attempt returns `WouldBlock` with the observed message. A second app-server's error is consistent with another active owner, including the production process, but it does not prove a stale lock or identify why `thread/read` waited. Deleting the lock is not supported by this evidence. [0.160.0 writer lock](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/rollout/src/writer_lock.rs)
- Protocol dispatch declares `thread/read` serialized by its `thread_id`, whereas `account/rateLimits/read` has `serialization: None`. The rate-limit implementation independently awaits authentication and backend rate-limit calls, including optional reset-credit details. The 10-second rate-limit timeout is therefore **not explained by the thread-ID serialization rule**. Shared process resources, backend latency, or an application-side request queue remain unverified possibilities, not source-backed diagnoses. [0.160.0 request definitions](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server-protocol/src/protocol/common.rs), [rate-limit processor](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server/src/request_processors/account_processor.rs)
