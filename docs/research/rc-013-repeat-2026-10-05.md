# RC-013 recurrence: Codex app-server 0.160.0 source check

Checked 2026-10-05 and updated 2026-10-06. This note concerns upstream contracts and reports. The local `codex --version` command returned `codex-cli 0.160.0`; the running backend launched `codex app-server` through PATH. Its exact resolved executable path was not independently read from the live process.

## Local recurrence evidence

The browser's authenticated `auth/session` returned 200 while the backend repeatedly logged `WebSocket /ws/chat 403`, with occasional accepted sockets. The configured remote Origin matched the page; local and CloudPub health checks returned 200. A fresh independent app-server returned models immediately and usage in about two seconds. Closing all CloudPub tabs removed the established backend connection. Reopening one tab briefly restored the UI before it lost the WebSocket again. These observations place the visible failure at FastAPI chat-connection ownership; they do not by themselves distinguish a retained socket, interrupted turn drain, failed accept, or a long-running handler operation.

Deterministic WebSocket tests exposed lock leaks in the application's existing handler: a missing terminal event after disconnect left subsequent valid sockets rejected with `1008: Chat is already in use`; a disconnect after `turn/completed` but before the following conversation-list send did the same. A failed WebSocket accept also leaked the claimed slot. The tests became green after moving completion state cleanup before the browser send, releasing the slot on accept failure, and bounding the disconnect drain. Additional red/green tests showed that shutdown of either the main bridge or a disposable history reader could stall after its request timeout. Both shutdown paths now have deadlines and abort only their own child process when necessary.

For history, a read-only five-chat probe against disposable app-server processes found that the most recent saved thread completed four `thread/items/list` pages (32 items), while another thread returned ten items then timed out on the next page. An owned disposable thread could be read through `thread/items/list` from a separate app-server without resuming it. These are direct local observations; the exact internal Codex wait remains unknown. The application now isolates paged reads for owned and unowned threads, with a deadline and a legacy fallback for unowned threads.

## Versioned protocol facts

- In the [0.160.0 protocol source](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L1570-L1617), `thread/read` defaults `includeTurns` to false. The source explicitly marks full-history hydration as deprecated for paginated threads and recommends a metadata-only read followed by `thread/turns/list` and `thread/items/list`. The latter methods have cursors and page limits; `thread/turns/list` defaults to descending order and summarized items. The [official app-server guide](https://learn.chatgpt.com/docs/app-server) calls `thread/turns/list` and `thread/items/list` experimental. The prior incident's local tests found that later item pages can also stall, so their existence is not proof of a complete workaround for the affected thread; see [the earlier research note](rc-013-codex-app-server-failure-surfaces.md#follow-up-saved-thread-read-and-writer-ownership).
- The [0.160.0 dispatch declarations](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server-protocol/src/protocol/common.rs#L807-L827) serialize `thread/read` by thread ID, while `thread/turns/list` and `thread/items/list` are explicitly concurrent. `turn/start` and `turn/interrupt` are also serialized by thread ID, but `model/list` has no such scope ([same source](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server-protocol/src/protocol/common.rs#L998-L1071)). A stuck same-thread read can therefore plausibly delay same-thread calls; these declarations alone cannot explain a global `model/list` timeout.
- The [official guide](https://learn.chatgpt.com/docs/app-server) specifies that a successful `turn/interrupt` ends with `turn/completed` and `status: "interrupted"`. The result of `turn/start` being accepted is not evidence of a completed inference turn; the terminal event and status must be observed. This is relevant if a reconnect follows a completed-looking browser response.
- The [0.160.0 release notes](https://github.com/openai/codex/releases/tag/rust-v0.160.0) describe fixes for SQLite stalls during connection setup and logging, plus clearer initialization errors. They do not claim to repair every history-hydration or post-turn stall. The unchanged CLI version cannot rule out runtime or upstream state changes.

## Remaining uncertainty

The live production process was not instrumented during the recurrence, so the exact event that left its slot occupied is not known. The logged 403 responses, authenticated session, and red regression tests establish the application's failure mode and validate the recovery changes. They do not prove that the same saved thread caused every rejected socket in this run. After a controlled backend restart with the new code, the user reported that CloudPub stayed connected with models and limits visible; selecting the previously problematic chat and reloading preserved the connection and data. The internal cause of the Codex history-page stall remains unknown.
