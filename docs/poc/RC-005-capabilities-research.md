# RC-005 — Codex app-server capabilities research

Checked 2026-10-04 against the official Codex app-server guide and OpenAI's generated protocol, then probed the installed `codex-cli 0.160.0` over stdio. The live observations below describe this machine's current account and catalog, not a fixed product-wide list.

## Model discovery and reasoning effort

`model/list` accepts optional `cursor`, `limit`, and `includeHidden`; its response is `{data: Model[], nextCursor: string | null}`. Model entries include `id`, wire `model`, `displayName`, `hidden`, `isDefault`, `supportedReasoningEfforts: {reasoningEffort, description}[]`, and `defaultReasoningEffort`. The effort type is an open string, so clients should display values from each model's returned list rather than assume a fixed enum. Paginate until `nextCursor` is null. The default call lists picker-visible models; `includeHidden: true` requests hidden models too. [Official guide](https://developers.openai.com/codex/app-server#list-models-modellist), [model list params](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/ModelListParams.ts), [model list response](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/ModelListResponse.ts), [model type](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/Model.ts), [effort option](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/ReasoningEffortOption.ts), [effort type](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/ReasoningEffort.ts).

The guide calls `defaultReasoningEffort` a **suggested default for clients** and says available models, efforts, and defaults depend on client and account. The catalog is not an entitlement check; a successful inference turn establishes access for that request. [Official app-server guide](https://developers.openai.com/codex/app-server#list-models-modellist), [official ChatGPT plan integration guide](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server).

The local `model/list {}` probe returned eight visible models and `nextCursor: null`. `gpt-6.1-sol` had `isDefault: true`, `defaultReasoningEffort: "low"`, and efforts `low`, `medium`, `high`, `xhigh`, `max`, `ultra`. This differs from the illustrative default in the guide, reinforcing that the live response must drive the selector. Other returned models were `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, and `gpt-5.5`. Evidence: local `codex-cli 0.160.0`, `python backend/poc/codex_app_server_poc.py models`, run 2026-10-04; schema generated with `codex app-server generate-ts --experimental`.

`turn/start` accepts optional `model` and `effort` overrides for the turn **and subsequent turns**. Omitting them preserves the thread's effective values. These are separate fields; the app-server does not require a nested model/effort object. [TurnStartParams](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/TurnStartParams.ts).

## In-flight turns

`turn/steer` appends input to the **active** turn without creating another turn. Its required params are `{threadId, input: UserInput[], expectedTurnId}`; the precondition must match the active turn. The response is `{turnId}`. It fails when no turn is active, emits no new `turn/started`, and does not accept turn setting overrides such as `model`. An optional `clientUserMessageId` is available. [Official app-server guide](https://developers.openai.com/codex/app-server#steer-an-active-turn), [TurnSteerParams](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/TurnSteerParams.ts), [TurnSteerResponse](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/TurnSteerResponse.ts).

`turn/interrupt` accepts `{threadId, turnId}` and returns `{}` when the interruption request succeeds. Observe `turn/completed` to learn the final outcome; a successful interruption ends with `turn.status: "interrupted"`. [Official app-server guide](https://developers.openai.com/codex/app-server#interrupt-a-turn), [TurnInterruptParams](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/TurnInterruptParams.ts), [TurnCompletedNotification](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/TurnCompletedNotification.ts).

## Collaboration modes and experimental gate

`collaborationMode/list` is experimental and has no pagination. The response is `{data: CollaborationModeMask[]}`; a mask has `name`, nullable `mode`, nullable `model`, and nullable `reasoning_effort`. `turn/start.collaborationMode` is also experimental. Its value is `{mode: "plan" | "default", settings: {model: string, reasoning_effort: string | null, developer_instructions: string | null}}`; when supplied, it takes precedence over the separate model, effort, and developer instruction fields. `developer_instructions: null` requests built-in instructions for the selected mode. [Official app-server guide](https://developers.openai.com/codex/app-server), [CollaborationModeListResponse](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/CollaborationModeListResponse.ts), [CollaborationModeMask](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/CollaborationModeMask.ts), [TurnStartParams](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/TurnStartParams.ts), [CollaborationMode](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/CollaborationMode.ts), [Settings](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/Settings.ts).

Experimental methods and fields require `initialize` with `capabilities.experimentalApi: true`; a stable client receives an error. The local 0.160.0 probe confirmed `collaborationMode/list {}` returns JSON-RPC `-32600` with `collaborationMode/list requires experimentalApi capability` when disabled. With opt-in, it returned `Plan` (`mode: "plan"`, `model: null`, `reasoning_effort: "medium"`) and `Default` (`mode: "default"`, `model: null`, `reasoning_effort: null`). The nullable mask is preset metadata, not itself a valid `turn/start.collaborationMode` value: resolve its missing model/effort into the full settings object before sending it. This last sentence is an inference from the two protocol types. [Official experimental opt-in guide](https://developers.openai.com/codex/app-server#experimental-api-opt-in), [InitializeCapabilities](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/InitializeCapabilities.ts), [CollaborationModeMask](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/CollaborationModeMask.ts), [CollaborationMode](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/CollaborationMode.ts).

## Integration implications

- Populate model and effort choices from `model/list`, using `isDefault` and each selected model's `defaultReasoningEffort` as the initial suggestions. Reconcile a selected effort when the model changes because effort support varies by model. This is an inference from the catalog fields and official guidance above.
- Send model/effort overrides on `turn/start`, and use `turn/steer` only for input to an already active turn with its known ID. For Stop, send `turn/interrupt` and retain the turn until its completion event. This follows the documented request and notification lifecycle.
- If Plan/Default mode selection is needed, opt into the experimental API explicitly and handle method rejection or catalog change. The local preset list is discovery data, not a permanent hard-coded mode list. This is an inference from the experimental contract and live response.
