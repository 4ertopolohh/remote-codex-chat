## Bridge implications

The current bridge uses the documented nested IDs, completion status, delta string, interrupt request, resume option, and `{decision: "decline"}` response. No correction to those shapes is needed. This is an inference from the schemas above and the current [bridge implementation](../../backend/codex_bridge/bridge.py) and [transport](../../backend/codex_bridge/_transport.py).

Two generated TypeScript types look stricter than their JSON wire schemas: `InitializeCapabilities` lists `requestAttestation`, and text `UserInput` lists `text_elements`, while both fields have defaults and are optional in the JSON schemas. The bridge's existing omissions are therefore valid. [Initialize JSON schema](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/json/v1/InitializeParams.json), [turn input JSON schema](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/json/v2/TurnStartParams.json).

If approval details are later displayed, parse command and file approval params separately: command approvals may carry `command`, `cwd`, `kind`, and `approvalId`; file approvals carry `reason` and optional `grantRoot`, rather than a `changes` array. The current bridge only declines them, so this does not affect its response. [Command request](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/CommandExecutionRequestApprovalParams.ts), [file request](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/typescript/v2/FileChangeRequestApprovalParams.ts).
